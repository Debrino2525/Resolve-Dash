# GhanaDash: going to production

This is the runbook for running GhanaDash for real customers and riders. It is ordered: do the
sections top to bottom the first time. `SETUP.md` covers local development.

## 1. What runs where

| Part | Production home | Address |
|---|---|---|
| Website (landing, privacy, terms) | Cloudflare Pages (live) | `https://ghanadash.globitechcybersolutions.com` |
| API (NestJS) + live dispatch | Always-on container host (Render blueprint included) | `https://ghanadash-api.globitechcybersolutions.com` |
| Admin portal | Same server as the API, on its own hostname | `https://ghanadash-admin.globitechcybersolutions.com` |
| Database, auth, document storage | Supabase (current project) | `https://<project-ref>.supabase.co` |
| Customer app / Rider app | Google Play + App Store, built with EAS | — |

**Why one level of subdomain** (`ghanadash-api.…`, not `api.ghanadash.…`): Cloudflare's free
certificate covers `*.globitechcybersolutions.com` only. Two-level names get HTTPS errors when
proxied unless you buy Advanced Certificate Manager.

**Why always-on, single instance:** the dispatch loop runs every 3 s inside the API process, and
SMS codes are held in memory. Serverless hosting (Workers, Vercel functions) can't run that, and
two instances would split SMS codes between them. One instance comfortably serves a city launch;
see section 9 before scaling out.

## 2. Supabase (same project as testing)

We decided to use one project, so be careful with test data (section 8 has the cleanup).

1. **Plan:** upgrade to **Pro** before launch. Free projects pause after a week without traffic
   and have no daily backups. Pro adds daily backups (enable Point-in-Time Recovery if budget
   allows).
2. **Authentication → URL Configuration**
   - **Site URL:** `https://ghanadash.globitechcybersolutions.com`
   - **Redirect URLs:** `ghanadash://**` and `ghanadash-rider://**`.
     Keep `exp://**` only while testing in Expo Go; **remove it on launch day**.
3. **Authentication → SMTP:** set up custom SMTP (e.g. Zoho Mail, Resend, Brevo) with
   `no-reply@globitechcybersolutions.com`. Supabase's built-in mailer sends only a few emails per
   hour, so password resets and sign-up emails would fail under real use.
4. **Authentication → Providers → Google:** in Google Cloud Console, **publish** the OAuth
   consent screen (app name GhanaDash, logo, privacy and terms URLs from the website, support
   email). Unpublished apps only let listed test users sign in.
5. **Database:** all three migrations in `supabase/migrations` applied (already done). Keep the
   `ghana_delivery_app` role password in your password manager; the API uses it via
   `DATABASE_URL` (SETUP.md §2).

## 3. Deploy the API and admin portal

The repo has a `Dockerfile` (runs anywhere) and `render.yaml` (Render blueprint).

**On Render (recommended):** Render → New → **Blueprint** → choose this GitHub repo. It creates
`ghanadash-api` (Docker, Frankfurt, Starter plan, health check `/health`). Then fill in the
secrets it asks for:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Supavisor connection string for `ghana_delivery_app` (SETUP.md §2) |
| `DATABASE_SSL_CA` | Supabase CA certificate **PEM text** (Project Settings → Database → SSL) |
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | Project URL and publishable key |
| `PAYSTACK_SECRET_KEY` | **Live** secret key (`sk_live_…`) |
| `MNOTIFY_API_KEY` | mNotify BMS key |
| `MAPBOX_ACCESS_TOKEN` | Server token (see §5) |

`PHONE_VERIFICATION_SECRET` and `ORDER_QUOTE_SECRET` are generated by Render. `NODE_ENV`,
`TRUST_PROXY`, `ADMIN_HOST`, `PAYSTACK_CALLBACK_URL` and `MNOTIFY_SENDER_ID` are preset in the
blueprint. Optional fare settings: `FARE_BASE_PESEWAS` (1800), `FARE_PER_KM_PESEWAS` (125).

**The server refuses to start if production settings are missing or unsafe** (missing secrets,
HTTP callback URL, Paystack test key, dispatch disabled…). The deploy log lists exactly what to
fix.

**Other hosts:** `docker build -t ghanadash-api .` then run with the same variables and
`NODE_ENV=production`, behind HTTPS, one instance, health check on `/health`.

## 4. DNS and protection (Cloudflare)

1. In Render → the service → **Settings → Custom Domains**, add
   `ghanadash-api.globitechcybersolutions.com` and `ghanadash-admin.globitechcybersolutions.com`.
2. In Cloudflare DNS add two **CNAME** records pointing at the `…onrender.com` name Render
   shows, **DNS only (grey cloud)** until Render shows the certificate as issued.
3. Optional afterwards: switch them to **Proxied** with SSL/TLS mode **Full (strict)**.
4. **Protect the admin portal with Cloudflare Access** (free up to 50 users):
   Zero Trust → Access → Applications → Self-hosted → `ghanadash-admin.globitechcybersolutions.com`
   → policy "Allow" → emails = your admin emails. Admins then pass a Cloudflare email code
   *before* the portal's own Supabase admin sign-in. With `ADMIN_HOST` set, the portal is not
   reachable through the API hostname. (Access needs the record **Proxied**; leave the API
   record DNS only.) Then set `CF_ACCESS_TEAM_DOMAIN` (e.g. `yourteam.cloudflareaccess.com`) and
   `CF_ACCESS_AUD` (the app's Audience tag) on the server: every admin-host request must then
   carry a valid Access pass, so the portal stays locked (403) even if the Access app or the
   proxied record is removed by mistake.
5. Check: `https://ghanadash-api.globitechcybersolutions.com/health` →
   `{"status":"ok","database":"ok"}`, and the admin hostname opens the portal.

## 5. Third-party services

- **Paystack:** switch to Live. Dashboard → Settings → API Keys & Webhooks → Webhook URL
  `https://ghanadash-api.globitechcybersolutions.com/webhooks/paystack`. The callback URL is set
  by the server.
- **mNotify:** the sender ID "GhanaDash" is approved for OTP. Keep the wallet topped up and
  enable low-balance alerts; when it runs dry, nobody can sign up.
- **Mapbox:** use two tokens. The **apps** get a public `pk.` token with only the default
  public scopes (it ships inside the app). The **server** gets its own token used only for
  Directions. Set a monthly usage alert in Mapbox → Account → Billing.

## 6. Mobile apps (EAS builds)

Testing stays on Expo Go for now. When ready for real builds:

1. Install the CLI and log in: `npm i -g eas-cli`, `eas login`.
2. Customer app only (rider app is already linked): in `customer-app/` run `eas init`.
3. Add the public config to each EAS project (not committed):
   ```
   eas env:create --environment production --name EXPO_PUBLIC_SUPABASE_URL --value https://<ref>.supabase.co --visibility plaintext
   eas env:create --environment production --name EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY --value <publishable key> --visibility plaintext
   eas env:create --environment production --name EXPO_PUBLIC_MAPBOX_TOKEN --value <app pk token> --visibility plaintext
   ```
   `EXPO_PUBLIC_API_URL` is already set to the HTTPS API in `eas.json`. Release builds refuse to
   start with a non-HTTPS API address.
4. **Still needed from you:** app icon (1024×1024 PNG) and splash image for each app.
5. Test build on a phone: `eas build -p android --profile preview` (installs as an APK).
6. Store builds: `eas build -p android --profile production` (AAB for Play) and
   `eas build -p ios --profile production`, then `eas submit`.
7. Store accounts: Google Play Console (one-time US$25), Apple Developer (US$99/year).
   Play's **Data safety** form: name, phone, email, approximate and precise location (rider: on
   duty only), photos (rider documents); none sold; encrypted in transit; deletion on request.

**Already production-grade in the code:** sessions are stored in the phone's encrypted keystore,
Google sign-in uses PKCE (one-time code, not tokens in the URL), and release builds require
HTTPS. **Planned for the build phase:** native Google sign-in (system account picker instead of
the browser tab), which needs a real build, not Expo Go.

## 7. Before launch: website and policies

- Privacy policy covers: rider on-duty location shared with the server for dispatch and
  tracking; customers see approximate positions of nearby riders; delivery contacts and
  addresses; rider documents. Redeploy `site/` to Cloudflare Pages after edits.
- Terms: cash on delivery, cancellation, the delivery PIN handover, prohibited items.

## 8. Launch day

1. In Supabase SQL Editor run `scripts/prelaunch-cleanup.sql`. It shows counts and rolls back;
   change the last line to `COMMIT` and run again to delete all test deliveries.
2. Delete test accounts in Supabase → Authentication → Users (keep your admin account).
3. Remove `exp://**` from Supabase Redirect URLs.
4. Confirm Paystack is on live keys (the server refuses test keys in production).
5. Smoke test with the store builds: sign up as a customer, approve a rider in the admin
   portal, go online, book, accept, pick up, deliver with PIN, rate.

## 9. Running it

- **Uptime:** add a free monitor (UptimeRobot or Better Stack) on
  `https://ghanadash-api.globitechcybersolutions.com/health`, alerting your phone and email.
- **Logs:** Render → service → Logs. Deploys restart cleanly (the server finishes requests, closes
  the database pool and stops dispatch).
- **Deploys:** pushing to `main` redeploys (blueprint `autoDeploy`). Use a branch and PR for
  changes; CI runs `npm run ci`.
- **Secrets:** never commit `.env`. Rotate a key by changing it in Render and redeploying; rotate
  `ORDER_QUOTE_SECRET` freely (open quotes just need refreshing), `PHONE_VERIFICATION_SECRET`
  freely (in-flight sign-ups retry their SMS code).
- **Scaling beyond one instance** (not needed at launch): move SMS codes to the database and run
  dispatch with a database lock (`pg_try_advisory_lock`) so only one instance dispatches.
